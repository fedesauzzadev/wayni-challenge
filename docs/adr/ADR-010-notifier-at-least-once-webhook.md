# ADR-010: Notifier at-least-once con Idempotency-Key declarativa

- **Estado**: Aceptado (actualizado en Oleada 4, DECIDE-P2.7b)
- **Contexto**: el notifier consume `import-completed` de SQS con fan-out secuencial a N notifiers (log estructurado siempre, webhook opcional) y aborta al primer fallo. El mensaje NO se borra si alguna notificación falla: SQS lo reentrega tras el visibility timeout, por lo que el webhook se entrega at-least-once. El outcome del handler se llama `Abandon`: no hay re-encolado, solo se abandona el mensaje y la visibilidad expira. La distinción `Skipped` vs `Delivered` para el webhook sin URL configurada quedó desestimada: la rama muerta del guard ya fue eliminada (el registro condicional en DI hace inalcanzable un `WebhookNotifier` sin URL).
- **Decisión**: aceptar la semántica at-least-once y declararla al receptor: el POST del webhook incluye el header `Idempotency-Key: <JobId>` para que el receptor dedupliche las re-entregas. El notifier NO persiste estado de entrega: sigue stateless; la deduplicación es responsabilidad del consumidor del webhook. `JobId` es la clave natural (un import completado = un evento).
- **Consecuencias**: sin infraestructura extra de idempotencia en el notifier y semántica honesta en código y docs. Riesgo residual asumido: si el receptor ignora el header, las re-entregas notifican dos veces; aceptable para notificaciones de fin de import. El consumer SQS además aísla cada mensaje del lote (try/catch por mensaje): una excepción no anticipada en un mensaje se loguea y no retrasa los demás (P3.7).
