# ADR-010: Notifier at-least-once sin idempotency key

- **Estado**: Aceptado
- **Contexto**: el notifier consume `import-completed` de SQS con fan-out secuencial a N notifiers (log estructurado siempre, webhook opcional) y aborta al primer fallo. El mensaje NO se borra si alguna notificación falla: SQS lo reentrega tras el visibility timeout. No existe idempotency key en el webhook: una reentrega puede notificar dos veces un mismo `ImportCompletedEvent`. El outcome del handler se llamaba `Requeue`, lo cual mentía (no hay re-encolado: solo se abandona el mensaje y la visibilidad expira). La distinción `Skipped` vs `Delivered` para el webhook sin URL configurada quedó desestimada: la rama muerta del guard ya fue eliminada en Oleada 2 (el registro condicional en DI hace inalcanzable un `WebhookNotifier` sin URL).
- **Decisión**: aceptar la semántica at-least-once del webhook tal cual, documentándola aquí en vez de agregar mecanismos de deduplicación (diferido a DECIDE-P2.7b). Renombrar el outcome `Requeue` → `Abandon` (y su log a "will return via visibility timeout") para que el código diga lo que hace: el mensaje se abandona y SQS lo reentrega. `ImportCompletedEvent` ya lleva `JobId` que el consumidor del webhook puede usar como clave natural de deduplicación si lo necesita.
- **Consecuencias**: semántica honesta en código y docs; sin infraestructura extra de idempotencia. Riesgo asumido: webhooks duplicados en reentregas (SQS garantiza at-least-once, no exactly-once); aceptable para notificaciones de fin de import. Si el endpoint requiere exactly-once, DECIDE-P2.7b evaluará una idempotency key (p. ej. `JobId` + retry dedupe en el consumidor).
