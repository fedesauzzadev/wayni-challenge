# ADR-011: Tuning de configuración sin paralelizar el pipeline de import

- **Estado**: Aceptado
- **Contexto**: el import del archivo mensual de deudores (5.9 GB, 34.4M de líneas → 19.9M de deudores agregados) tarda ~16 min en el entorno dev. Desglose medido con las métricas `bcra_import_phase_duration` (segunda corrida): staging 372s, agregación 360s, índices 242s. El GROUP BY corría con `work_mem=4MB` (spill a disco de una tabla hash de ~20M de grupos), los `CREATE INDEX` con `maintenance_work_mem=64MB` (sort externo) y el bulk generaba checkpoints cada ~1GB de WAL (`max_wal_size=1GB`) — todo defaults de Postgres.
- **Decisión**: se acepta el tiempo de procesamiento como problema de **configuración, no de arquitectura**:
  - `docker-compose.yml` (servicio `postgres`): `shared_buffers=512MB`, `max_wal_size=4GB`, `checkpoint_timeout=15min`, `max_parallel_maintenance_workers=4`.
  - `DapperImportJobRepository`: `SET work_mem='2GB'` en `AggregateImportAsync` y `SET maintenance_work_mem='512MB'` en `CreateImportIndexesAsync`, ambos **session-scoped** (Npgsql resetea la sesión al devolver la conexión al pool: ninguna otra query los ve). El 2GB se justifica porque la tabla hash de ~20M de grupos necesita ~2-3GB y el consumo es de un único nodo en una única sesión; el techo de seguridad es la VM de Docker (15.5GB compartidos con el resto del compose) frente al riesgo de OOM-kill del backend a mitad de la agregación.
  - Expectativa honesta: ~16 min → 11-12 min. El archivo se procesa una vez por mes; no hay SLA que justifique más.
- **Alternativas consideradas y rechazadas por ahora (sobreingeniería para la cadencia actual)**. Se deja constancia de que son viables y cuál sería su costo real si la cadencia o el SLA cambian:
  - **Staging paralelo** (N workers parseando rangos de bytes disjuntos — `S3FileSource` ya soporta byte-offset): cirugía sobre el protocolo lease/checkpoint (`CommitBatchAsync` confirma COPY + checkpoint por lote de 200k en UNA transacción; paralelizar exige reordenar la contabilidad de `bytes_committed`/líneas y el takeover). Ganancia estimada: 372s → ~100s.
  - **Pre-agregación sharded por `hash(cuit)` + merge final** (SUM/MAX componen): agrega K tablas de staging, un paso de merge y más superficie de fallo en la fase que hoy es un solo `INSERT ... SELECT ... GROUP BY` idempotente. Ganancia estimada: 360s → 60-90s.
  - **Particionar `deudor_agg`/`entidad_agg` por `LIST (import_id)`**: eliminaría la penalidad de coexistencia (~90s medidos: el import nuevo escribe mientras la tabla retiene los 19.9M de filas del activo hasta el swap), pero toca migraciones, query-service, swap y cleanup. Es la primera candidata si se retoma la optimización.
  - **Cambiar el sustrato** (BigQuery/Snowflake/Redshift — el ELT ya es set-based, Citus, o Spark): infraestructura nueva para un job mensual. Ganancia estimada: <2 min.
  - **Eliminar la doble copia del upload local** (browser → BFF → `DATA_DIR` → ingestion): la idempotencia depende del sha256 del archivo completo calculado en el BFF y el retry del multipart; requiere presigned URLs de S3 y cambia las garantías de entrega.
- **Consecuencias**: mejora inmediata sin tocar código de dominio, protocolos ni contratos; reversible (los `SET` mueren con la sesión, el compose es un override de arranque). Costo asumido: el tiempo sigue siendo de minutos y mono-worker por diseño (ADR-006: un solo import activo). **Gatillos para revisar esta decisión**: cadencia diaria o menor, SLA de ventana de corte, o crecimiento superlineal del archivo.
