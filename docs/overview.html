Presentación del repositorio

Wayni Challenge

Pipeline ELT de deudores bancarios (BCRA): ingestion → agregación → swap → consulta. Tres microservicios .NET con minimal APIs sobre PostgreSQL, con observabilidad OpenTelemetry de punta a punta.

.NET 10 C# · Minimal APIs PostgreSQL 16 Docker Compose LocalStack · S3 + SQS OpenTelemetry Prometheus Grafana xUnit + Testcontainers

01Resumen ejecutivo

Qué es este repositorio, en seis puntos.

  • Pipeline ELT que procesa la publicación diaria de Información de deudores del BCRA (dataset de muestra: ~5,9 GB, 34.385.567 líneas) y publica una versión agregada consultable mediante swap atómico de la versión activa.
  • Tres microservicios .NET (minimal APIs) — ingestion, query y notifier — sobre PostgreSQL, con LocalStack (S3 + SQS) para el entorno local vía docker compose.
  • Concurrencia resuelta 100 % en la base de datos: FOR UPDATE SKIP LOCKED + lease con heartbeat, índice único parcial para un solo import activo e INSERT ... ON CONFLICT DO NOTHING para idempotencia. Sin locks distribuidos ni afinidad de sesión.
  • Resiliente por diseño: reanudación desde checkpoint sin duplicar filas, takeover de workers caídos al vencer el lease, y detección de fuente modificada (ETag/size).
  • Observabilidad integrada: OpenTelemetry en los 3 servicios, /metrics en formato Prometheus y dashboard de Grafana aprovisionado, sin setup manual.
  • Performance medida con el dataset real: end-to-end ≈ 486 s (~8 min), con ~78.400 líneas válidas/s en la fase de staging.

02Objetivo del challenge

La necesidad que cubre el sistema.

Construir un pipeline ELT de deudores financieros bancarios (publicación diaria del BCRA, sección Estadísticas → Información de deudores) que recorra ingestion → agregación → swap → consulta:

  • Ingerir un archivo diario grande (~5 GB por publicación) desde fuentes locales (/data) o S3 (s3://bucket/key), con uploads idempotentes.
  • Tolerar fallos: un worker que cae o pierde la conexión a mitad del import no debe perder trabajo ni duplicar filas; otro worker retoma.
  • Garantizar una única versión publicada: los consumidores consultan siempre una versión consistente de los agregados (nunca un estado mixto durante el reemplazo).
  • Notificar la finalización del import (log estructurado + webhook opcional) y observar el proceso batch: throughput, duración por fase y estado de los jobs.

03Cómo se resolvió la necesidad

Tres servicios con responsabilidad única, coordinados por PostgreSQL.

Bcra.Ingestion

Acepta uploads idempotentes (POST /imports) y orquesta el import bajo lease (ImportJobProcessor): reclamo SKIP LOCKED → staging → agregación → índices pre-swap → swap atómico → DROP del import anterior. Migraciones DbUp.

Las fuentes se rutean por esquema (RoutingFileSourceFactory): s3://bucket/key → S3FileSource (rango bytes=offset- para reanudar, ETag real, buckets restringidos por allow-list), el resto → LocalFileSource. Al completar, publica ImportCompletedEvent en SQS de forma best-effort.

Bcra.Query

Lee la versión publicada resolviendo active_import, con conexiones de solo lectura y sin locks: las lecturas son MVCC y durante el swap ven la versión vieja o la nueva, nunca un estado mixto.

Bcra.Notifier

Consume import-completed con long-poll (SqsImportCompletedConsumer): notifica vía log estructurado siempre y webhook HTTP si Notifications:WebhookUrl está configurado; borra el mensaje solo si la notificación fue OK (si falla, vuelve por visibilidad). El readiness incluye chequeo de SQS.

El truco del ELT

Cada lote confirma el COPY binario a staging + el checkpoint (bytes_committed, líneas, ETag/size, heartbeat) en una transacción READ COMMITTED: no existe lote en staging sin su checkpoint, por lo que reanudar no duplica filas. La agregación es SQL (GROUP BY) y la re-agregación es idempotente (DELETE previo por import_id).

04Decisiones clave

Resumen de los ADRs 005–009 (detalle completo en docs/adr/).

ADR-005

Reclamo con FOR UPDATE SKIP LOCKED + lease

Aceptado Contexto

Varios workers deben consumir jobs de import_job sin duplicar trabajo ni bloquearse; un worker puede caer a mitad de un import y su trabajo debe retomarse.

Decisión

Reclamar en una transacción READ COMMITTED corta con SELECT ... FOR UPDATE SKIP LOCKED (candidatos: Pending, o Loading/Aggregating con heartbeat vencido) seguida de UPDATE que setea lease_owner y heartbeat_at. Renovación periódica solo por el dueño; takeover al vencer el lease; abort inmediato ante DbException.

Consecuencias

Sin colas de mensajes extra ni locks distribuidos; los workers no se bloquean entre sí y la recuperación es automática. El trabajo no confirmado se re-ejecuta (la idempotencia por (source, etag, periodo) mitiga el re-procesamiento).

Ver ADR completo →

ADR-006

Un solo import activo con índice único parcial

Aceptado Contexto

El pipeline garantiza un único import activo (Loading/Aggregating) para que el swap de active_import y la publicación sean consistentes. Alternativas: advisory lock de sesión o constraint en base de datos.

Decisión

Índice único parcial uq_import_job_single_active ON import_job ((1)) WHERE status IN ('Loading','Aggregating'). La activación que colisiona recibe 23505 y se trata como "no se pudo activar": el job queda Pending y el worker lo reintenta, sin fallar.

Consecuencias

Sin afinidad de sesión (el lock de sesión de pg_try_advisory_lock es incompatible con PgBouncer en transaction pooling) y crash-safe: la verdad vive en la fila, no en memoria de sesión. La lógica de reintento debe tolerar 23505 como caso normal.

Ver ADR completo →

ADR-007

READ COMMITTED en todas las escrituras

Aceptado Contexto

Se necesita exclusión mutua (reclamo, import activo, swap) pero con alta concurrencia de lecturas del query-service. SERIALIZABLE añade retrabajo por serialización y LOCK TABLE serializa de más.

Decisión

Todas las transacciones de escritura se abren explícitamente con IsolationLevel.ReadCommitted. La exclusión mutua se logra con mecanismos puntuales: FOR UPDATE SKIP LOCKED (reclamo), FOR UPDATE en la fila única de active_import (swap) e índices únicos (idempotencia e import activo).

Consecuencias

0 usos de SERIALIZABLE o LOCK TABLE; menos conflictos y retrabajos. Cada camino crítico tiene su mecanismo explícito, documentado en el README.

Ver ADR completo →

ADR-008

Sin lock distribuido

Aceptado Contexto

Con múltiples instancias de workers/API se podría introducir un lock distribuido (Redis, ZooKeeper, advisory locks de sesión) para coordinar el reclamo y el import activo.

Decisión

No introducir lock distribuido: toda la coordinación es de base de datos — SKIP LOCKED + lease con heartbeat (ADR-005), índice único parcial para el import activo (ADR-006) e INSERT ... ON CONFLICT DO NOTHING para idempotencia.

Consecuencias

Menos piezas operativas (sin Redis/ZooKeeper, sin afinidad de sesión, compatible con connection pooling) y crash-safe por diseño. La base centraliza la contención; el lease tiene una ventana de vencimiento y los imports se serializan (aceptable: es un requerimiento).

Ver ADR completo →

ADR-009

Observabilidad con OpenTelemetry

Aceptado Contexto

El pipeline es un proceso batch largo (staging → agregación → índices → swap) ejecutado por un worker en background: sin métricas no hay forma de saber throughput, duración por fase ni estado de los jobs sin consultar la base.

Decisión

Registrar OpenTelemetry (SDK, runtime ASP.NET + HTTP) en los 3 servicios vía el helper compartido AddObservability, exportando métricas a formato Prometheus en /metrics — sin collector ni OTLP: Prometheus scrapea directamente. Métricas custom del pipeline en el meter Bcra.ImportPipeline. El correlation-id se propaga como tag correlation_id del trace y el TraceId se agrega al LogContext de Serilog. El compose agrega Prometheus (9090) y Grafana (3000) con datasource + dashboard aprovisionados.

Consecuencias

Observabilidad de punta a punta con stack estándar y cero setup manual; el throughput queda medible, habilitando el tuning de batch/pool basado en datos. El dashboard es provisionado (no editable desde la UI sin desactivar el provisioning) y las métricas viven en memoria del proceso (la historia queda en Prometheus).

Ver ADR completo →

El repositorio además documenta las decisiones estructurales previas en docs/adr/: ADR-001 (PostgreSQL como persistencia), ADR-002 (ELT: staging then SQL), ADR-003 (situación de máximo literal) y ADR-004 (base compartida entre servicios).

05Arquitectura y composición del sistema

Pipeline ELT con 3 microservicios (.NET, minimal APIs) y PostgreSQL.

Flujo de un import (concurrencia)

  1. Upload idempotente: POST /imports hace INSERT ... ON CONFLICT (source, etag, periodo) DO NOTHING; duplicado → devuelve el job existente con alreadyExisted=true (201 nuevo / 200 existente).
  2. Reclamo: ClaimNextAsync selecciona el job más antiguo elegible (Pending, o Loading/Aggregating con lease vencido) con FOR UPDATE SKIP LOCKED y lo reclama (lease_owner, heartbeat_at). Si la activación choca con el índice único parcial de import activo, el job queda Pending y se reintenta.
  3. Ejecución: el procesador crea la partición de staging, agrega, renueva lease, crea índices (CREATE INDEX, antes del swap), swapea active_import (transacción corta) y marca Completed. Cada lote confirma COPY + checkpoint en UNA transacción READ COMMITTED; la re-agregación es idempotente y la pérdida de conexión aborta sin confirmar nada. Si la fuente cambió (ETag/size), el job termina Failed en vez de reintentar para siempre.
  4. Notificación: post-Completed se publica ImportCompletedEvent (JobId, líneas, agregados, duración) en la cola SQS import-completed (best-effort). Notifier lo consume con long-poll (20 s), notifica y borra el mensaje solo si la notificación fue OK; mensajes malformados se descartan.
  5. Limpieza: post-swap, DROP de la partición de staging e índices del import anterior (nunca del activo, sin DELETE masivo).

Build, tests, stack completo y observabilidad.

Build y tests

dotnet build Bcra.Microservices.sln
dotnet test tests/unit/Bcra.Ingestion.Domain.Tests
dotnet test tests/unit/Bcra.Ingestion.Application.Tests
dotnet test tests/unit/Bcra.Ingestion.Infrastructure.Tests
dotnet test tests/unit/Bcra.Notifier.Application.Tests
dotnet test tests/integration/Bcra.Ingestion.IntegrationTests   # requiere Docker (Testcontainers)

Stack completo (compose)

docker compose up -d --build                                    # stack completo con LocalStack + Prometheus + Grafana
docker compose exec localstack awslocal sqs list-queues         # cola import-completed
docker compose exec localstack awslocal s3 ls                   # bucket bcra-local
curl http://localhost:18082/health/ready                        # notifier (incluye chequeo SQS)
curl http://localhost:18080/metrics                             # métricas ingestion (formato Prometheus)
curl http://localhost:18081/metrics                             # métricas query
curl http://localhost:18082/metrics                             # métricas notifier
curl http://localhost:9090/api/v1/targets                       # 3 targets en "up"

Al levantar el compose, localstack/init/01-init.sh crea el bucket S3_BUCKET (por defecto bcra-local) y la cola import-completed (idempotente). Ingestion publica ahí el ImportCompletedEvent al completar un import y notifier lo consume; si WEBHOOK_URL se configura, notifier además hace HTTP POST del evento.

Fuentes de datos

El ingestion-service lee desde DATA_DIR (por defecto ./samples), definido en .env. Las fuentes se rutean por esquema: s3://bucket/key → S3 (LocalStack o AWS real, buckets restringidos a la allow-list Ingestion:AllowedS3Buckets), el resto → archivos locales bajo la allow-list de directorios (Ingestion:AllowedSourceDirs, montado como /data en el compose).

Para correr localmente, descargar los archivos de texto de "Información de deudores" publicados diariamente por el BCRA en www.bcra.gob.ar (sección Estadísticas → Información de deudores) y ubicarlos en samples/:

Tuning aplicado, justificado por la medición:

  • CommandTimeout=0 en los comandos pesados (AggregateImportAsync, CreateImportIndexesAsync, DropImportStorageAsync): el default de Npgsql (30 s) es menor que la agregación medida (132 s) — sin esto, el import del dataset real entraba en loop de takeover (timeout → DbException → lease vencido → re-agregación idempotente que volvía a expirar). La reanudación por checkpoint ya cubre fallos reales de conexión.
  • Batch size 200k y pool 50 se mantienen: la medición no muestra cuello de botella del lado .NET (el limiter es Postgres en la agregación).
