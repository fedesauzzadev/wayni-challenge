Cómo funciona la ingesta del archivo de deudores

Diagrama completo del pipeline tal como funciona hoy: desde la subida del archivo hasta la publicación atómica de los agregados, con los tiempos reales medidos sobre el dataset de 5,9 GB (34.385.567 líneas → 19.926.199 deudores, 485 entidades). Total end-to-end ≈ 11,5 min.

El flujo completo, paso a paso

0

Upload vía BFF — el nombre del archivo no importa browser + BFF

La web sube el multipart al BFF (POST /api/imports/upload): archivo + periodo + referencias opcionales + destino (local o s3). El BFF calcula el sha256 del contenido y lo usa como etag; la key de guardado se deriva del contenido, no del nombre:

-- storage local (default de la UI): copia al DATA_DIR montado como /data:ro
uploads/<periodo>/deudores-<sha256[0..16]>.txt      -- mismo contenido ⇒ misma key, siempre
uploads/<periodo>/Maeent.txt · Nomdeu.txt            -- referencias, por periodo

Luego llama al ingestion: POST /imports con {source, etag, size, periodo} + X-Api-Key (secreto que solo vive en el BFF).

Regla operativa: renombrar el archivo no fuerza reimport (source y etag son del contenido). Referencias por periodo: si es un periodo nuevo y no van adjuntas, el import falla — la UI lo advierte.

1

Idempotencia del upload 1 query

INSERT INTO import_job (id, source, etag, size, periodo, status, created_at)
VALUES (...) ON CONFLICT (source, etag, periodo) DO NOTHING;

Si insertó → 201 Created, job Pending. Si ya existía → 200 OK devolviendo el job existente (alreadyExisted=true) cuando está en curso o es el publicado: re-subir el mismo archivo en el mismo periodo es un no-op. Si el existente es un terminal no publicado (Failed o Completed sin agregados), se descarta en la misma transacción y se crea la corrida nueva.

2

Reclamo del worker (lease) SKIP LOCKED

El worker (dentro del ingestion-API) hace polling. Reclama el job más antiguo elegible — Pending o con heartbeat_at vencido (60 s) — con FOR UPDATE SKIP LOCKED y lo activa: Pending → Loading, setea lease_owner y heartbeat.

Un índice único parcial sobre estados Loading/Aggregating garantiza un solo import activo a la vez: si choca (23505), el job queda Pending y se reintenta — no falla.

Invariante: a lo sumo 1 import ejecutándose; N workers no se bloquean entre sí (SKIP LOCKED).

3

Staging — COPY por lotes + checkpoint atómico 251,5 s medidos

Se crea la partición debt_staging_<importId> (particionada por import). Loop: leer el archivo desde bytes_committed (reanudable), parsear 200k líneas por lote (clase Record / Control 98-99 / Invalid) y confirmar COPY binario + checkpoint en UNA transacción READ COMMITTED:

-- por cada lote, atómico:
COPY debt_staging_<importId> FROM STDIN (FORMAT BINARY);
UPDATE import_job SET bytes_committed=…, lines_…=…, heartbeat_at=now WHERE id=@id AND lease_owner=@me;

No existe lote en staging sin su checkpoint ⇒ reanudar nunca duplica filas. Si el worker cae, el lease vence y otro retoma desde el checkpoint. ~136.700 líneas/s · 172 lotes.

Estado: Loading → Aggregating al consumir el archivo completo.

4

Agregación SQL (GROUP BY) 298,9 s medidos

Sobre una conexión con SET work_mem='2GB' (sessional, muere con la conexión):

DELETE FROM deudor_agg  WHERE import_id=@id;              -- re-agregación idempotente
INSERT INTO deudor_agg  SELECT import_id, cuit, MAX(situacion), SUM(monto)
                         FROM debt_staging_<id> GROUP BY cuit;
INSERT INTO entidad_agg SELECT import_id, entidad, SUM(monto)
                         FROM debt_staging_<id> GROUP BY entidad;
UPDATE import_job SET deudores_count=…, entidades_count=…, suma_total=…;

34,4 M de filas → 19,9 M de deudores + 485 entidades. El 2 GB de work_mem evita el spill a disco de la tabla hash (ADR-011); el resto del tiempo es I/O.

5

Índices pre-swap 137,4 s medidos

Con SET maintenance_work_mem='512MB': 3 índices parciales por import (solo tocan las filas del import nuevo) + VACUUM ANALYZE para que las queries del import ya publicado usen index-only scans. Se crean ANTES del swap: al publicar, todo ya está indexado.

6

Swap atómico de la versión publicada 0,03 s

SELECT import_id FROM active_import WHERE id=1 FOR UPDATE;   -- lock de la fila única
UPDATE active_import SET import_id=@nuevo WHERE id=1;

Los lectores del query-service resuelven active_import con MVCC: durante el swap ven la versión vieja o la nueva, nunca un estado mixto. El job pasa a Completed.

7

Post-Completed: notificación + cleanup del anterior best-effort · ~2 min

Se publica ImportCompletedEvent en SQS (si falla, se loguea y no rompe el import) → notifier envía el email a los registrados (Mailpit en dev). Luego el cleanup del import anterior: DROP de su partición de staging, DROP de sus índices parciales y DELETE de sus ~20 M de agregados — nunca del activo. Por eso el import siguiente corre con la tabla "convivida" (costo asumido, ver ADR-011).

Modelo de datos del pipeline (ER)

publicación (swap) máquina de estados datos crudos del import agregados (leídos por query) maestros de referencia relación lógica (sin FK física)

Sin FKs físicas deliberadamente: staging y agregados se crean/borran por import_id con DDL (DROP de particiones, índices parciales) — una FK obligaría a borrar en orden y acoplaría el cleanup. El query-service siempre filtra por el import_id de active_import.

Las 3 invariantes que sostienen todo

🔁 Idempotencia por (source, etag, periodo)

Source y etag se derivan del contenido (sha256). Re-subir el mismo archivo en el mismo periodo devuelve el job existente sin reprocesar. Solo un cambio de contenido o de periodo genera corrida nueva.

1️⃣ Un solo import activo

Índice único parcial sobre Loading/Aggregating. Sin él no habría swap consistente: agregar un worker escala la cola, no la velocidad de un archivo (ADR-006).

🧗 Reanudable sin duplicar

Lote a staging + checkpoint en la misma transacción + lease con heartbeat: un worker caído pierde el lease, otro retoma desde bytes_committed y la re-agregación es idempotente (DELETE previo).
